알게 된 것

1. **DDS ONLINE은 콘솔 페이지가 열려 있어야 켜진다.** [확인] 콘솔 페이지의 스크립트는 1초마다 `POST /browser/session?client=<id>`를 보내고, 배지 문구는 `/vehicle/state`의 `gear.bridge_ready`로 정한다. 에뮬레이터 부팅 뒤 5분 동안 브라우저 없이 기다렸을 때는 `bridge_ready=false`였고, 같은 하트비트를 보내자 곧바로 `true`가 됐다. 다른 팀도 "브라우저 창이 열려 있어야 값을 바꿀 수 있다"고 적었다 [자기 보고]. 시연과 녹화 때는 콘솔 페이지를 계속 열어 둔다. 자동 검증 때는 같은 하트비트를 셸에서 보낸다.
2. **에뮬레이터의 화면 사용자는 10번이다.** [확인] `am get-current-user` = 10. 다른 팀 보고와 같다.
3. **콘솔의 기어 카드는 AAOS 표준 `GEAR_SELECTION`(0x11400400)이 아니라 `VENDOR_GEAR_SELECTION`(0x21400400)을 낸다.** [확인] `/vehicle/catalog`의 `gear-selection.car_property`. 설계는 표준 `GEAR_SELECTION`을 읽기로 했으므로 표준 속성으로도 바뀌는지 G1에서 확인한다.
4. 콘솔 카드와 차량 속성: 좌석 착석 `SEAT_OCCUPANCY`(0x15400BB0), 문 `DOOR_POS`(0x16400B00), 창문 `WINDOW_POS`(0x13400BC0), 방향지시등 `TURN_SIGNAL_STATE`(0x11400408). [확인] `/vehicle/catalog`.
5. `avdmanager`는 이 이미지를 받지 않는다(이미지 폴더 이름 `pleos_car_emulator`와 `source.properties`의 태그 `android-automotive`가 달라서). Android Studio 없이 쓸 때는 AVD `config.ini`를 직접 쓴다. [확인]
6. GPU는 문서의 최소 사양(RTX 3060급)보다 낮은 내장 GPU지만 `-gpu host`로 부팅과 화면 표시는 됐다. [확인]

## G1 신호 — 통과 (2026-11-11)

방법: `tools/verify_g1.py`가 콘솔 페이지와 같은 HTTP 경로(`PUT /vehicle/seat|body|gear|turn-signal`)로 값을 바꾸고, 앱이 `MB.Signal` 태그로 남긴 로그 줄의 시각과 비교한다. 게스트와 호스트의 시계 차는 `adb shell date`로 보정했다(오차 ±10ms 수준이라 일부 지연이 음수로 찍힌다).

| 확인할 것 | 결과 | 증거 |
|---|---|---|
| 좌석 착석 콜백(운전석, 동승석, 뒷좌석 좌·우) | [확인] 네 좌석 모두 콜백이 온다. 지연 10ms 이내 | `evidence/g1/latency.md`, `evidence/g1/logcat_MB.Signal.txt` |
| 문 콜백(네 문) | [확인] 열림 `pos=1`, 닫힘 `pos=0`. 지연 10ms 이내 | 같은 곳 |
| 창문 콜백(네 창문) | [확인] 콜백이 온다. 단 값의 단위가 10% (아래 2) | 같은 곳 |
| 기어 | [확인] AAOS `GEAR_SELECTION`과 Pleos SDK `Gear` 모두 P·R·N·D를 따라간다 | 같은 곳 |
| 방향지시등(2순위용) | [확인] Vehicle SDK `TurnSignal` 콜백 `LEFT`, `OFF` | 같은 곳 |
| 1초 안에 찍힘 | [확인] 28개 변경 중 27개가 50ms 안에 찍혔다. 남은 1개(창문 3%)는 값이 바뀌지 않아 콜백이 없는 것이 맞다(아래 2) | `evidence/g1/latency.md` |
| 착석 값 반전 | **[확인] 반전된다.** 콘솔에서 Occupied로 바꾸면 SDK는 `false`, Empty로 바꾸면 `true`를 준다. 네 좌석 모두 같다. 앱 시작 때 `getCurrentSeatOccupancy`도 콘솔의 Empty를 `true`로 준다 | `evidence/g1/latency.md` 1~7행 |

알게 된 것과 정한 것

1. **착석 값은 반전돼 온다.** 다른 팀 셋의 보고[자기 보고]와 같다. 앱 설정에 "착석 값 뒤집기"를 두고 기본값을 켜 둔다(이 에뮬레이터 기준). 실차에서 반전이 없으면 끈다.
2. **창문 위치는 0~10 단위로 온다.** [확인] `checkWindowPositionCapabilities`가 네 창문 모두 `0..10`을 준다. 콘솔의 30%는 `pos=3`, 100%는 `pos=10`, 2%와 3%는 `pos=0`이다. 앱은 범위로 나눠 %로 바꾼다. 그래서 설계의 창문 기준 2%는 사실상 "10% 이상 열리면 열림"으로 동작한다. 기준값 설정은 남겨 두되 이 차에서 의미 있는 값은 0 또는 10의 배수다.
3. **문 위치는 `0..1`, 트렁크(`REAR`)와 후드(`HOOD`)는 `0..100`이다.** [확인] 문지기는 네 승객 문만 본다. 트렁크와 후드는 보지 않는다(설계 범위).
4. **좌석 capability에 `ROW_2_CENTER`도 있다.** [확인] 콘솔에는 이 좌석 카드가 없다. 설계대로 운전석, 동승석, 뒷좌석 좌·우 넷만 본다. [추정] 실차에서 뒷좌석 가운데를 볼지는 나중 일이다.
5. **기어는 설계대로 AAOS `CarPropertyManager`의 `GEAR_SELECTION`으로 읽는다.** [확인] 콘솔 카드는 `VENDOR_GEAR_SELECTION`을 내지만 표준 `GEAR_SELECTION` 콜백도 함께 온다(Pleos SDK 콜백보다 4~36ms 늦음). Pleos 문서의 "SDK API 정책"도 표준에 있는 것은 표준 API를 쓰라고 한다 [문서]. 권한은 `android.car.permission.CAR_POWERTRAIN`.
6. **설계 문서와 다른 사실: Vehicle SDK 2.3.2에는 `Gear` 도메인이 있다.** [확인] `Vehicle.getGear()`, `getCurrentGearSelectionState`, `registerGearSelection`, 권한 `pleos.car.permission.CAR_DRIVE`. 공개 문서의 도메인 표에는 없다. 쓰지 않으므로 권한도 선언하지 않는다.
7. Vehicle SDK의 콜백은 메인 스레드가 아닌 바인더 스레드로 온다. [확인] 로그의 스레드 번호. 상태는 스레드 안전한 `StateFlow`로 모은다.

## G2 오디오 — 조건부 통과 (2026-11-11)

방법: `tools/verify_g2.py`. 측정용 신호음(`tools/make_temp_song.py probe`: 반주 무음 + 보컬 880Hz)을 4채널 FLAC으로 재생하면 출력 크기가 곧 보컬 음량이다. 호스트 기본 출력의 모니터를 48kHz로 녹음하고, 받은 조각마다 호스트 시각을 붙인다. 노래방 상태에서 콘솔로 동승석 문을 연 호스트 시각부터, 녹음에서 소리가 커지기 시작한 때(10%)·절반(50%)·다 올라온 때(90%)까지를 잰다. 5번 되풀이.

| 확인할 것 | 결과 | 증거 |
|---|---|---|
| 4채널 디코딩 | [확인] 에뮬레이터의 `c2.android.flac.decoder`가 quad FLAC을 푼다. 2채널 대안은 쓰지 않아도 된다 | logcat `MediaCodec ... c2.android.flac.decoder` |
| 두 갈래가 어긋나지 않음 | [확인] 반주와 보컬이 한 파일의 같은 프레임에 있고 처리기 하나가 같은 표본에서 섞는다. 구조상 어긋날 수 없다 | `app/.../audio/StemMixProcessor.kt` |
| 노래방일 때 가수 음량 | [확인] 평소의 0.19배(설정 20%) | `evidence/g2/result.md` |
| 딸깍 소리 | [확인] 0개. 표본 간 점프가 880Hz 사인파의 최대 기울기 1.6배를 넘는 곳이 없다 | 같은 곳 |
| 끊김 | [확인] 0개. AudioFlinger 언더런 카운터도 0 | 같은 곳, `dumpsys media.audio_flinger` |
| 신호→소리 변화 0.3초 이내 | **안드로이드 출력 기준 통과, 호스트 스피커 기준 미달.** 아래 표 | `evidence/g2/result.md`, `evidence/g2_buf100/result.md` |

지연 나누기(AudioTrack 버퍼 40ms, 5회 중앙값)

| 구간 | 값 | 근거 |
|---|---|---|
| 콘솔 PUT → 앱의 신호 콜백 | 약 5ms | G1 측정 |
| 콜백 → 믹서가 음량을 올리기 시작 | 약 15ms | 앱 로그 `reactionMs`(당시 상수 100ms를 더한 값 111~120ms에서 뺌) |
| 믹서 → 안드로이드 오디오 출력 | 232ms | `dumpsys media.audio_flinger`의 우리 트랙 Latency(버퍼 2124프레임 ≈ 48ms + 플랫폼 약 184ms) |
| **소계: 신호 → 안드로이드 출력** | **약 250ms** | 위 셋의 합 |
| 안드로이드 출력 → 호스트 스피커(에뮬레이터 → PipeWire) | 약 145ms | 호스트 녹음 중앙값 395ms에서 소계를 뺌 |
| 호스트 녹음에서 커지기 시작(10%) | 375~410ms, 중앙값 395ms | `evidence/g2/result.md` |

알게 된 것과 정한 것

1. AudioTrack 버퍼를 100ms(Media3 기본보다 작게 잡은 첫 값)에서 40ms로 줄이자 호스트 기준 지연이 445ms에서 395ms로 줄었다. 40ms에서도 언더런과 끊김이 없었다. [확인] `AudioConfig.PCM_BUFFER_US = 40_000`.
2. 남은 지연의 대부분은 앱 밖이다. 플랫폼의 출력 경로(약 184ms)와 에뮬레이터의 호스트 오디오 전달(약 145ms)은 앱에서 바꿀 수 없다. [추정] 실차의 출력 경로 지연은 이 에뮬레이터와 다를 수 있다.
3. 0.3초 목표는 안드로이드 출력 기준으로는 맞고, 영상에 담기는 호스트 소리 기준으로는 약 0.1초 늦다. 영상과 README에는 "신호에서 차 오디오 출력까지 약 0.25초(에뮬레이터에서는 호스트 전달 약 0.15초가 더해짐)"라고 쓴다.
4. 대피 시간 기록은 "신호가 도착한 때 → 믹서가 음량을 올리기 시작한 때 + 출력 지연 232ms"로 계산한다. 출력 지연 232ms는 이 에뮬레이터에서 잰 값이다(`AudioConfig.OUTPUT_LATENCY_MS`).
5. FLAC 블록 크기를 1024표본으로 작게 묶는다(`tools/pack_stems.py`). 처리기에 한 번에 들어오는 양이 작아야 음량 변화가 늦게 반영되지 않는다.
6. 측정 중 실수: 첫 측정은 신호음 곡(300초)이 끝나 다음 곡(음악)으로 넘어간 뒤에 돌아 숫자를 버렸다. 신호음을 900초로 늘려 다시 쟀다.
7. 대기 시간 버그를 고쳤다. 재생 버튼으로 문지기를 깨울 때 마지막 차 신호 시각을 기준으로 넘겨 대기가 5초가 아니라 3.7초였다. 차 신호가 새로 들어온 경우에만 그 시각을 쓰게 고친 뒤 5.002초. [확인] 앱 로그 `ARMING 05:08:29.204 → KARAOKE 05:08:34.206`.

알게 된 것과 정한 것

1. 미디어 키를 넣은 결과: NEXT 뒤 곡이 `측정용 신호음 → 임시곡 하나`, PAUSE 뒤 `PAUSED`, PLAY 뒤 `PLAYING`, PREVIOUS 뒤 다시 `측정용 신호음`. [확인]
2. **내비 안내가 나올 때 우리 앱에는 포커스 손실이 오지 않는다.** [확인] 내비(`ai.umos.maps.android.navigation.app`)는 `USAGE_ASSISTANCE_NAVIGATION_GUIDANCE`로 `GAIN_TRANSIENT_MAY_DUCK`을 요청하고, `CarAudioFocus`는 기존 보유자(우리 ExoPlayer)를 둔 채 허가한다(포커스 가이드의 NAVIGATION↔MUSIC 공존 C). 안내가 끝나면 내비가 포커스를 반납한다. 녹음에서 내비 효과음과 안내 음성은 신호음과 함께 나왔고, **이 에뮬레이터에서는 음악이 줄지 않았다**(신호음 크기 약 1.0배 유지). 앱은 재생을 이어 갔다.
3. 그래서 설계 4절의 "일시적 손실 때 감쇄냐 일시정지냐"는 내비 안내에서는 일어나지 않았다. 앱에 `LOSS_TRANSIENT_CAN_DUCK`이 오면 ExoPlayer 기본대로 감쇄하고(포커스 가이드의 권장 매핑과 같음), `LOSS_TRANSIENT`(Gleo 호출 등)이 오면 일시정지하고, `LOSS`가 오면 Music/Audio 가이드대로 `stop()` 한다. [추정] 실차에서는 오디오 HAL이 감쇄할 수 있다.

[추정] 그래서 시스템 미디어 앱 라이브러리에는 나오지 않을 수 있다(가이드의 표).
